# 场景 A 键与宝可梦中心电脑交互

## 1. 协议含义与客户端证据

**C2S `0x27` 是无目标参数的场景 A 键兜底请求，不是电脑专用请求。**
按 A 可能是在尝试访问商店店员、其他 NPC、电脑、背景物件或空地，不能只凭 opcode
认定为电脑交互。客户端参考项目为 `C:\Users\z3407\Desktop\28887-obf-project`：

- `src/main/java/f/ga0_0.java` 的 `AUx`：检查朝向格、柜台和可交互实体，命中 NPC 时发送
  `cb_1`；未命中该分支时发送 `lpt1__0`，没有先判断目标是否为电脑。
- `src/main/java/f/cb_1.java`：构造器 `super(34)`，编码 NPC Object ID 和签名哈希。
- `src/main/java/f/lpt1__0.java`（原名 `f.LpT1`）：构造器 `super(39)`，编码方法为空。

| opcode | 方向 | payload | 字段顺序 |
| --- | --- | ---: | --- |
| `0x27` | C2S | 0 字节 | 无坐标、无朝向、无 NPC ID、无目标类型 |
| `0x22` | C2S | 16 字节 | NPC Object ID `long LE`，签名哈希 `long LE` |
| `0x21` | C2S | 2 字节 | 交互次数 `byte`，选择值 `byte` |
| `0x27` | S2C | 1 字节 | PC 窗口开关 `boolean`，与 C2S 含义不同 |

上述请求无字符串编码或终止符。`0x22` 保留既有哈希算法；非法长度走协议解码错误路径，
哈希不匹配记录日志并断开，不会因事件开关关闭而跳过报文校验。

用户抓包为单字节 `27`，服务端位置为 `(0,5,3,3,3,2)`。地图资源
`resource/map/kanto/viridian_city_mart/ViridianCity_Mart.json` 对应 `(0,5,3)`，其中店员
`npc_0` 位于 `(2,3,0)`，脚本键为 `ViridianCity_Mart_EventScript_Clerk`。
**若玩家朝左 `toward=2`，则朝向格命中该店员；原日志没有朝向，不能据它断定客户端为何未发 `0x22`。**

## 2. 服务端分流与边界

`EmptyInteractPacket` 保留 C2S `0x27` 注册，只做空 payload 校验并转交
`org.pokemmo.gameserver.game.interact.SceneInteractionService`。NPC 脚本可能等待动作，
因此与 `StartTalkPacket`、`InteractPacket` 一样使用现有脚本长操作队列。

1. 校验角色、当前地图与在线位置一致，以及非战斗、非交易、无其他交互。
2. 按在线朝向 `0=下、1=上、2=左、3=右` 查找朝向格中已加载、可交互的 NPC。
   GBA 高度按客户端的非负层值 `/3` 分组比较，负层兼容；NDS 当前只允许相同层。
3. 只有地图明确提供 `MB_COUNTER` 时才向前多查一格，不能把普通障碍格或附近 NPC
   当作隔柜台交互。常磐市商店通过 `interactionCounters` 明确标记 `(3,3)`，
   让玩家在 `(4,3)` 朝左时匹配 `(2,3)` 的店员。命中 NPC 后不再尝试电脑分支。
4. 没有 NPC 目标时，才检查已确认的电脑位置和向上朝向，交给 `PcInteractionService`。
5. 其他情况记录 `目标=背景事件` 或 `目标=未匹配`，不打开 PC、不修改交互状态。

`StartTalkPacket` 的 C2S `0x22` 继续按客户端明确提供的实体 ID 在当前地图查找，
并复用同一 NPC 脚本入口；不会用服务端模板坐标覆盖客户端已命中的游走 NPC。
两条路径均拒绝未加载或不可交互的 NPC。`MapFile` 将资源的 `npcs[].script` 保存在
`NpcEntity.interactionScriptName`，不改变 `npc_N` 的实体名称，也不改变 NPC 发包格式。
2026-09-09 已移除旧脚本键/实体名称查找分支；新真新镇模块按原地图键和固定 NPC 序号接管开场，
NPC 的显示、目标位置和交互权限使用玩家独立投影，详见 [真新镇剧情](PALLET_TOWN_STORY.md)。

店铺 JSONC 的 `npcs`（地图名与 NPC 序号）或兼容旧地图 `shopId` 绑定的 NPC
优先进入 `game.shop.ShopService`，不受剧情事件开关影响；
店铺定义按地区/城市存放在 `resource/shop`，配置独立买入和回收价。
旧客户端只读浏览，完成 `0xDC` 能力协商的客户端使用报价和事务买卖，
详见 [`NPC_SHOP_PACKET.md`](NPC_SHOP_PACKET.md)。
其他 NPC 若未接入新剧情，记录 `NPC 交互未处理: 脚本尚未实现`，不会因为缺失脚本卡在对话状态。
真新镇使用独立 `STORY` 状态与内容开关；实际剧情结束或异常时清理状态，异常保留中文日志。
该分流本身不新增数据库写入；PC/GTL/邮箱仍调用既有查询和客户端刷新链路。

## 3. 电脑菜单

电脑业务位于 `org.pokemmo.gameserver.game.interact.PcInteractionService`。
常磐市宝可梦中心一楼沿用以下已确认位置表示，**且必须朝上 `toward=1`**：

```text
(0, 5, 4, 11, 2, 0)  // 登录后当前状态
(0, 5, 4, 11, 1, 2)  // 移动到电脑前
(0, 5, 4, 11, 2, 2)  // 地图层坐标
```

服务端随后发送 S2C `0x21` 的 `MULTICHOICE` 交互（客户端线值为 `36`，不是内部脚本值
`31`）。标题字符串 ID 为 `2350`；包尾三个字节使用客户端内置菜单表选择器
`category = 10`、`menuId = 3`、`flags = 0`，客户端据此读取以下选项：

| 返回值 | 字符串 ID | 含义 |
| ---: | ---: | --- |
| `1` | `2351` | `{玩家游戏ID}的电脑` |
| `2` | `2352` | 交易行 |
| `3` | `2353` | 邮箱 |
| `4` | `53` | 取消 |

标准 `MULTICHOICE` 回执是 1-based。选择 PC 会复用 `//pc` 的容器和箱子初始化顺序；选择
交易行会查询默认的宝可梦第一页；选择邮箱会发送邮箱计数和收件箱第 0 页。取消或非法
选项会清理当前菜单状态；角色不在指定地图坐标、战斗中、交易中或已有其他交互时不会
打开菜单。交易行和邮箱窗口的具体客户端开窗由现有列表/计数响应初始化，未在服务端
新增 opcode。选择邮箱会同时记录当前 Session 的邮箱已打开状态；该状态只在通过此 PC 菜单
进入邮箱后成立，关闭邮箱、移动、换地图或重连后清除。
