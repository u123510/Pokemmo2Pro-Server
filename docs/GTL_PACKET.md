# GTL 交易行封包

## 当前范围

服务端已实现宝可梦上架、查询、购买和取消挂单，以及物品/时装上架、查询和购买：

- C2S `0x9A` 创建宝可梦或物品挂单；
- C2S `0x9C` 购买宝可梦或物品挂单，S2C `0x9C` 返回 GTL 操作结果；
- C2S `0x9D` 取消自己创建的宝可梦挂单；
- C2S `0x9E` 批量领取自己已成交挂单的款项；
- C2S `0x9F` 请求当前角色的 GTL 购买记录，S2C `0x5E` 返回近期交易活动；
- C2S/S2C `0x9B` 查询宝可梦、物品公开列表或自己的混合挂单；
- 上架成功后扣除手续费、将宝可梦移入 `auction` 容器，并刷新角色金钱与 PC 槽位；
- 物品上架成功后将拥有道具移入 `void` 背包，刷新角色金钱、主背包和当前 GTL 页面；
- 取消成功后将宝可梦从 `auction` 容器返还到原 PC 槽位（冲突时使用下一个空槽）。

物品取消、除名称索引集合、性别、性格、等级、孵蛋年份、IV、努力值、个体值匹配数量、特性、隐藏仅雌性种族、隐藏百变怪、蛋组、闪光、粒子、已学习技能、隐藏特性、头目类型、时装部位和价格范围外的筛选规则执行、以及过期回收尚未实现；形态变化已解锁规则 `24` 当前仅保证协议可解析，具体行为见下文。

## 创建挂单 `0x9A`

用户提供的宝可梦上架抓包：

```text
9A 00 00 10 C2 CC 93 00 00 00 90 D0 03 00 01 00
```

用户提供的时装上架抓包，单价为 `10000`、数量为 `1`：

```text
9A 01 00 10 82 73 D7 00 00 00 10 27 00 00 01 00
```

除 opcode 外的 payload 固定为 15 字节：

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | ---: | --- |
| listingType | byte | `0` | `0` 宝可梦，`1` 物品 |
| objectId | long LE | `634795462656` | 宝可梦或拥有道具的 Object ID |
| unitPrice | int LE | `250000` | 单价 |
| amount | short LE | `1` | 宝可梦固定为 `1` |

客户端 `f.dt0_0` 的写入顺序为：

```text
listingType -> objectId -> unitPrice -> amount
```

宝可梦必须属于当前角色、位于 PC 容器且未被重复上架。物品必须属于当前角色、位于
`inventory_id = 1` 主背包、数量充足且不能是账号绑定物品。普通物品使用
`ItemManager.isTradeableForExchange` 的客户端兼容判定：`Item.bin` 中由
`ItemDataReader` 暴露的 `isTradeAble` 是打包字节的一部分，不是可直接使用的布尔交易开关；
服务端按客户端默认允许交易，并排除客户端已确认的特殊不可交易索引区间。可穿戴时装继续使用
`SkinType` 的 item index 到 addon ID 映射判定。最低
单价为 `1000`；手续费为总价的 `5%`，最低 `1000`、最高 `25000`。

物品全量上架时保留原 Object ID，并把该 `owned_item` 移到 `inventory_id = 0` 的 `void`。
部分堆叠上架时，服务端减少原背包记录数量，并用雪花 ID 创建一条只包含上架数量的
`void` 记录，挂单关联新 Object ID。拆分、扣费和挂单写入位于同一事务中。

上架事务成功后，服务端依次发送：

```text
0x9C 操作成功
0x0C 角色金钱更新
0x15 从 PC 容器移除已上架的宝可梦
```

物品/时装上架成功后发送：

```text
0x9C 操作成功
0x0C 角色金钱更新
0x40 完整主背包刷新
0x9B 当前交易行页面刷新（会话存在最近查询时）
```

此前 ITEM 分支固定返回 `9C 00 01`，客户端把拒绝结果显示为“未知错误”。当前 ITEM
分支进入真实上架事务，成功值为 `9C 00 00`；失败仍返回拒绝，服务端日志用于区分归属、
数量、账号绑定、可交易标志、价格和余额等失败原因。`itemIndexId=2287`（熔岩兜帽）可映射到
HAT addon，因此即使资源中的 `isTradeAble=false` 也按可穿戴时装处理；普通道具
`itemIndexId=1476` 也不会再因该字段被误判。

不再向已经打开的 PC 窗口发送完整 `0x13` 容器快照，因为客户端可能替换容器控制器但
保留窗口中的旧槽位引用，导致数据库已经移走宝可梦而界面仍显示旧精灵。

## 移除宝可梦 `0x15`

客户端当前协议分支的 `f.ho_1` 在 S2C opcode `0x15` 创建 `f.R3`。`f.R3` 按以下顺序
读取并调用当前场景容器的按 Object ID 删除方法：

| 字段 | 类型 | 上架时的值 | 说明 |
| --- | --- | ---: | --- |
| containerType | byte | `0` | `PokemonContainerType.PC` |
| pokemonObjectId | long LE | 上架请求的 `objectId` | 要从客户端容器删除的宝可梦 |

完整封包长度为 `10` 字节：`1` 字节 opcode 加 `9` 字节 payload。服务端由
`SendRemovePokemonPacket` 编码该响应；客户端 `f.R3` 会在已有 PC 容器控制器上直接删除
目标条目并标记容器需要刷新。

例如上架 Object ID `634795462656` 后，预期发送：

```text
15 00 00 00 10 C2 CC 93 00 00
```

## 操作结果 `0x9C`

客户端 `f.ND0` 读取一个 byte，并映射到 `f.td_1`：

| result | 当前服务端含义 | 客户端行为 |
| ---: | --- | --- |
| `0` | 成功 | 清空上架表单并刷新按钮状态 |
| `1` | 请求被拒绝 | 显示客户端本地化提示并重新启用提交按钮 |

S2C `0x9A` 在客户端对应邮件附件领取确认 `f.TH0`；它与本处 C2S `0x9A` 方向不同，
不能作为 GTL 上架请求的响应。

## 购买挂单 C2S `0x9C`

用户提供的购买抓包：

```text
9C 03 00 00 00 00 00 00 00 01 00
```

客户端 `f.vc_1` 固定按以下顺序写入：

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | ---: | --- |
| listingId | long LE | `3` | 要购买的 GTL 挂单 ID |
| amount | short LE | `1` | 宝可梦固定为 `1`；物品为本次购买数量，必须大于 `0` 且不超过挂单剩余数量 |

宝可梦购买时，服务端在同一事务中锁定挂单、买家角色和拍卖容器中的宝可梦，并校验：
挂单仍为活跃宝可梦挂单、尚未过期、不是买家自己的挂单、数量为 `1`、余额足够且 PC 有空位。
成功后扣除买家金钱，将宝可梦的 `trainer_id` 改为买家、移动到 PC 空槽，并把挂单更新为
`status = 1`、`sold_amount = 1`。

物品购买时，服务端在同一事务中锁定挂单、买家角色和卖家 `void` 背包中的
`owned_item`，校验挂单剩余数量、有效期、余额、道具归属和客户端可交易规则。完整购买会将
原 `owned_item` 转入买家主背包；部分购买会减少卖家 `void` 记录数量，并用新的 Object ID
创建买家主背包记录。成交数量累加到 `sold_amount`，只有全部数量售出时才将挂单标记为
`status = 1`；卖家仍通过 `0x9E` 领取成交款。

宝可梦购买成功响应顺序为：

```text
0x0C 买家金钱更新
0x14 向买家 PC 容器添加成交宝可梦
```

物品购买成功响应顺序为：

```text
0x0C 买家金钱更新
0x40 买家主背包完整刷新
0x9B 当前交易行页面刷新（会话存在最近查询时）
```

购买成功不发送 S2C `0x9C`：客户端把该包的成功码固定显示为“上架成功”，而没有购买专用
成功提示。购买失败仍发送 S2C `0x9C` 结果值 `1`，用于恢复客户端按钮状态并显示错误。

购买成功后，服务端会使用该会话最近一次 `0x9B` 查询保存的请求序号、列表类型和页码，
主动重发当前 `0x9B` 页面，确保公开列表或“我的商品”列表立即移除已售挂单。卖家的
个人挂单查询会继续返回已售记录，直到卖家通过 C2S `0x9E` 成功领取成交款。

购买被拒绝时，服务端仍会发送合法的 `0x9C` 结果包（结果值 `1`）。客户端可能将该结果
显示为“未知错误”，这是客户端本地化提示的表现，不代表封包解析失败。服务端日志会记录
具体拒绝原因，包括挂单不存在、购买自己的挂单、挂单已售/过期、余额不足、数量超出剩余
挂单数量、道具不在卖家的 `void` 背包中，或宝可梦不在卖家的 `auction` 容器中。交易测试
需要使用不同于卖家的角色购买；同一角色购买自己的挂单会被服务端拒绝。

## 近期交易记录 C2S `0x9F` / S2C `0x5E`

客户端在交易行第四个页签激活时发送 C2S `0x9F`。请求没有 payload；服务端必须返回
S2C `0x5E`，而不是回送 `0x9F`。客户端的 `f.O5` 按以下顺序读取：

```text
groupCount: unsigned byte
groups: groupCount * {
  tradedAt: long LE             // Unix epoch milliseconds
  tradeType: byte               // 2 = GTL
  entryCount: unsigned byte     // 当前每个 GTL 成交为 2
  entries: entryCount * {
    itemIndexId: short LE       // 0 = 没有道具
    pokemonDexId: short LE      // 0 = 没有宝可梦
    amount: int LE              // 道具数量、货币金额或宝可梦数量
    sent: byte                  // 1 = 发送，0 = 收到
  }
}
```

每个购买记录编码为两条：先是 `sent = 1` 的成交金额，随后是 `sent = 0` 的商品。
宝可梦条目保存图鉴 ID 和成交时的携带道具索引；物品条目保存物品索引和购买数量。
服务端按成交时间倒序最多返回 `255` 条，空记录返回单个 `00` 字节的合法空列表。

购买事务会在同一数据库事务中写入 `gtl_trade_history`；扣钱、资产转移、挂单数量更新或
历史写入任一失败都会整体回滚。历史查询只返回当前角色作为 `buyer_id` 的 GTL 购买记录，
不暴露其他玩家数据。该表在实现前的已成交挂单没有买家与分笔成交信息，无法可靠补录，
因此旧成交不会出现在该页；从应用 DDL 后的新购买开始记录。

## 领取成交款 C2S `0x9E`

客户端 `f.pz_0` 先写一个 unsigned byte 数量，再按顺序写入每个挂单 ID 的 `long`。用户
提供的领取一个挂单的抓包为：

```text
9E 01 06 00 00 00 00 00 00 00
```

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | ---: | --- |
| count | unsigned byte | `1` | 待领取挂单数量，范围 `1..255` |
| listingIds | `count * long LE` | `6` | 每个待领取的 GTL 挂单 ID |

服务端要求 payload 长度恰为 `1 + count * 8`，拒绝空列表、零或负 ID、重复 ID，以及未加载
角色的请求。随后在一个事务内按 ID 顺序锁定所有目标挂单和卖家角色；每条挂单必须归当前
卖家所有、处于 `status = 1` 已售状态，且 `0 < sold_amount <= amount`。成交额按
`unit_price * sold_amount` 累加，超出 Java `int` 金钱协议范围时整体拒绝，不会部分入账。

成功时事务先更新 `character.money`，再将所有目标挂单标为 `status = 3`（已领取）。该状态
保留 `sold_amount` 历史，同时使同一挂单无法二次领取；个人 GTL 列表只查询 `status = 0/1`，
因此刷新后已领取条目会消失。这个实现不新增数据库列，也不修改运行中的数据库 schema。

成功响应顺序为：

```text
0x9C 操作成功
0x0C 卖家金钱更新
0x9B 当前交易行页面刷新（会话存在最近查询时）
```

任一挂单不存在、归属不符、未售、已领取、字段异常或金额溢出时，服务端仅发送 `0x9C`
拒绝结果，并保持所有挂单和金钱不变。

## 取消挂单 C2S `0x9D`

客户端取消自己的宝可梦挂单时发送一个 8 字节的小端挂单 ID：

```text
9D 03 00 00 00 00 00 00 00
```

其中 `03 00 00 00 00 00 00 00` 是 `listingId = 3`。服务端只允许挂单卖家本人
取消仍处于 `status = 0` 且尚未成交的宝可梦挂单，并在事务中锁定挂单和 `auction`
容器中的宝可梦。成功后将挂单标记为 `status = 2`，把宝可梦归还卖家 PC，并发送：

```text
0x9C 结果成功
0x14 PC 新增宝可梦
```

客户端不会仅凭 `0x9C` 成功结果自动从“我的商品”列表移除旧条目。服务端因此会在
取消成功后，按照会话最近一次 `0x9B` 查询保存的请求序号、列表类型和页码，额外重发
当前 `0x9B` 页面。由于查询只返回活跃挂单（个人列表另外保留已售记录），已取消的
挂单不会继续显示，也不会再次触发可重复下架操作。

取消不退还上架手续费。若原 PC 槽位已经被占用，服务端会选择卖家 PC 的下一个空槽，
并在 `0x14` 的完整宝可梦数据中返回实际位置。

## 查询列表 `0x9B`

客户端打开或刷新交易行时发送：

```text
9B 01 00 00 00 00 00
```

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | ---: | --- |
| requestTimes | byte | `1` | 请求序号 |
| listType | byte | `0` | `0` 宝可梦，`1` 物品，`2` 我的挂单 |
| searchFilterType | byte | `0` | 示例为 `NEWEST` |
| pageIndex | short LE | `0` | 从 `0` 开始的页码 |
| ruleSize | byte | `0` | 后续筛选规则数量 |

`searchFilterType` 已应用到宝可梦、物品和“我的挂单”三个分页查询：

| 值 | 枚举 | SQL 排序 |
| ---: | --- | --- |
| `0` | `NEWEST` | 创建时间降序、挂单 ID 降序 |
| `1` | `EARLIEST` | 创建时间升序、挂单 ID 升序 |
| `2` | `LOWEST_PRICE` | 单价升序，再按创建时间和挂单 ID 降序 |
| `3` | `HIGHEST_PRICE` | 单价降序，再按创建时间和挂单 ID 降序 |

例如 `9B 03 00 03 00 00 00` 请求宝可梦公开列表第 `0` 页并按最高价排序。服务端会把
排序类型与请求序号、列表类型、页码和名称索引集合一起保存在 Session 中；上架、购买或
取消后主动重发当前页面时继续使用相同排序，不会退回默认的 `NEWEST`。

服务端 S2C `0x9B` 页头：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| requestSequence | byte | 回显 `requestTimes` |
| listType | byte | 回显列表类型 |
| pageIndex | short LE | 回显页码 |
| totalListings | int LE | 符合条件的挂单总数 |
| entryCount | byte | 当前页条目数，服务端页大小为 `10` |

服务端在每次合法查询时保存该会话的请求序号、列表类型和页码。上架、购买或取消成功
后会按这份状态重新构造当前页并重发 `0x9B`，请求序号必须原样回显；客户端会丢弃与其
当前列表序号不一致的响应，因此不能固定使用 `requestTimes = 1`。

### 名称搜索规则 `0`

客户端不会把搜索栏中的文本直接发给服务端，而是先在本地将名称匹配为当前列表的
索引 ID 集合。宝可梦页使用图鉴 ID，物品页使用 item index ID。例如在宝可梦页输入
“妙”会发送：

```text
9B 02 00 00 00 00 01 00 03 00 03 00 02 00 01 00
```

规则 `0` 的字段顺序为：

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | ---: | --- |
| ruleType | byte | `0` | 当前列表的名称匹配索引规则 |
| matchCount | unsigned short LE | `3` | 后续索引 ID 数量 |
| listingIndexIds | `matchCount * unsigned short LE` | `3, 2, 1` | 宝可梦页为图鉴 ID，物品页为 item index ID |

客户端会先在本地按当前语言的显示名称匹配索引集合，再把匹配结果发送给服务端。宝可梦
列表在 `gtl_listing.object_id = pokemon.id` 的关联查询上应用 `pokemon.dex_id IN (...)`；
物品列表在 `gtl_listing.object_id = owned_item.item_id` 的关联查询上应用
`owned_item.item_index_id IN (...)`。总数查询和分页数据查询必须使用相同条件；会话状态也
分别保存宝可梦图鉴 ID 与物品索引 ID，确保上架后的主动页面刷新不会丢失搜索条件。

### 性格规则 `2`

规则 `2` 后跟一个 unsigned byte 性格索引，范围为 `0..24`，与
`PokemonNatureType` 的编号一致。例如指定乐天 `LAX(9)`：

```text
9B 0A 00 00 00 00 01 02 09
```

服务端将性格规则保存进会话的当前 GTL 请求状态，并在宝可梦关联查询中应用与
`Math.floorMod(personalityValue, 25)` 等价的 SQL 条件。这样也能正确处理负数
`personality_value`。总数查询、分页查询以及上架/购买/取消后的主动页面刷新都会保留该
条件。物品公开列表不会应用宝可梦性格条件。

### 价格规则 `9/10`

规则 `9` 后跟一个 signed int LE 最小价格，规则 `10` 后跟一个 signed int LE 最大价格。
两端都包含在筛选范围内；只发送其中一条规则时，另一端不设限制。价格必须为非负数，
同时发送时最小价格不能高于最大价格。价格筛选与列表排序独立，排序字段仍由请求头的
`searchFilterType` 决定。

最小价格为 `1000` 的请求：

```text
9B 04 00 00 00 00 01 09 E8 03 00 00
```

最大价格为 `1000` 的请求：

```text
9B 05 00 00 00 00 01 0A E8 03 00 00
```

同时限制 `500..1000` 的请求：

```text
9B 06 00 00 00 00 02 09 F4 01 00 00 0A E8 03 00 00
```

服务端对宝可梦、物品和“我的挂单”使用相同的 `unit_price >= minPrice` 与
`unit_price <= maxPrice` 条件。该范围保存到 Session，主动刷新当前 GTL 页面时继续复用。

### 等级规则 `3/4`

规则 `3` 后跟一个 unsigned byte，表示宝可梦最低等级；规则 `4` 后跟一个 unsigned
byte，表示宝可梦最高等级。等级范围为 `1..100`，两端都包含；只发送其中一条规则时，
另一端不设限制，同时发送时最低等级不能高于最高等级。等级条件使用
`pokemon.level_value >= minLevel` 与 `pokemon.level_value <= maxLevel`，仅作用于宝可梦条目。

最低等级为 `11` 的请求：

```text
9B 07 00 00 00 00 01 03 0B
```

服务端日志会输出：

```text
宝可梦最低等级限制: 11
```

最高等级为 `100` 时，规则 `4` 后的值为 `64`（十六进制）：

```text
9B 08 00 00 00 00 01 04 64
```

同时限制等级 `11..100` 时，客户端会携带两条规则：

```text
9B 09 00 00 00 00 02 03 0B 04 64
```

### 孵蛋年份规则 `15`

规则 `15` 后跟两个 unsigned int LE Unix 秒时间戳，分别表示年份起始时间和结束时间，
客户端按起止时间的开区间判断（时间戳必须大于起点且小于终点）。例如客户端选择 `2012`
年时发送：

```text
9B 04 00 00 00 00 01 0F 00 A2 FF 4E FF 26 E2 50
```

其中 `0x4EFFA200` 为 `2012-01-01 00:00:00 UTC`，`0x50E226FF` 为
`2012-12-31 23:59:59 UTC`。服务端日志会输出解析后的年份和原始时间戳：

```text
规则类型: 15 (EGG_YEAR)
蛋年限制: 2012
蛋年时间范围: min=1325376000, max=1356998399
```

时间范围保存在 Session，并应用于公开宝可梦列表和“我的挂单”的宝可梦条目；物品条目
不受此条件影响。当前 schema 没有独立的孵蛋日期字段，查询使用 `pokemon.catch_time`
作为客户端蛋年日期来源，并按 UTC 转为 `TIMESTAMP` 开区间比较。

### 个体值规则 `5/6`

规则 `5` 后跟一个 unsigned byte 属性索引和一个 signed short LE 个体值，表示该属性的
最低 IV；规则 `6` 使用相同字段表示最高 IV。属性索引与数据库 `iv_values` 数组一致：

| 索引 | 属性 | 数据库数组位置 |
| ---: | --- | ---: |
| `0` | HP | `iv_values[1]` |
| `1` | 攻击 | `iv_values[2]` |
| `2` | 防御 | `iv_values[3]` |
| `3` | 特攻 | `iv_values[4]` |
| `4` | 特防 | `iv_values[5]` |
| `5` | 速度 | `iv_values[6]` |

IV 索引必须为 `0..5`，IV 值必须为 `0..31`。最低和最高规则可以分别指定不同属性；只有
在两条规则指定同一属性时才校验最低值不能高于最高值。服务端日志会输出属性名称和值，
例如用户抓包 `9B 08 00 00 00 00 01 06 05 00 00`：

```text
最大IV限制索引: 5 (速度)
最大IV限制值: 0
```

公开宝可梦列表使用 `iv_values[index + 1] >= minValue` 和
`iv_values[index + 1] <= maxValue` 条件；“我的挂单”对物品条目跳过 IV 条件，仅筛选其中
的宝可梦条目。总数查询、分页查询和上架/购买/取消后的当前页面刷新都会复用这些条件。

### 努力值规则 `17/18`

规则 `17` 表示最低努力值，规则 `18` 表示最高努力值。两条规则的字段顺序相同：一个
unsigned byte 属性索引，后跟一个 unsigned short LE 努力值。属性索引与数据库
`ev_values` 数组一致：

| 索引 | 属性 | 数据库数组位置 |
| ---: | --- | ---: |
| `0` | HP | `ev_values[1]` |
| `1` | 攻击 | `ev_values[2]` |
| `2` | 防御 | `ev_values[3]` |
| `3` | 特攻 | `ev_values[4]` |
| `4` | 特防 | `ev_values[5]` |
| `5` | 速度 | `ev_values[6]` |

努力值索引必须为 `0..5`，努力值必须为 `0..255`。最低和最高规则可以分别指定不同属性；
当两条规则指定同一属性时，服务端校验最低值不能高于最高值。例如抓包
`9B 05 00 00 00 00 01 12 01 00 00` 表示攻击的最高努力值为 `0`：

```text
规则类型: 18 (MAX_EV)
最大努力值限制索引: 1 (攻击)
最大努力值限制值: 0
```

公开宝可梦列表使用 `ev_values[index + 1] >= minValue` 和
`ev_values[index + 1] <= maxValue` 条件；“我的挂单”对物品条目跳过努力值条件，仅筛选
其中的宝可梦条目。总数查询、分页查询和上架/购买/取消后的当前页面刷新都会复用这些条件。

### 个体值匹配数量规则 `19`

规则 `19` 后跟一个 unsigned short LE，表示至少需要拥有多少个满 IV（值为 `31`）的属性。
当前宝可梦有六项 IV，因此客户端值必须为 `0..6`。例如搜索至少六项满 IV：

```text
9B 06 00 00 00 00 01 13 06 00
```

服务端日志会输出：

```text
规则类型: 19 (IV_MIN_MATCH)
最小个体值匹配数量: 6
```

查询使用 `cardinality(array_positions(iv_values, 31)) >= count`。该条件会保存到 Session，
并在公开列表、“我的挂单”以及上架、购买、取消后的当前页面刷新中复用；“我的挂单”中的
物品条目跳过宝可梦 IV 条件。

### 蛋组规则 `7`

规则 `7` 后跟一个 unsigned byte 蛋组索引。客户端索引与服务端 `PokemonEggGroupType` 一致：

| 索引 | 蛋组 |
| ---: | --- |
| `1` | 怪兽组 |
| `2` | 水 1 组 |
| `3` | 虫组 |
| `4` | 飞行组 |
| `5` | 陆上组 |
| `6` | 妖精组 |
| `7` | 植物组 |
| `8` | 人形组 |
| `9` | 水 3 组 |
| `10` | 矿物组 |
| `11` | 不定形组 |
| `12` | 水 2 组 |
| `13` | 百变怪组 |
| `14` | 龙组 |
| `15` | 未发现蛋组 |
| `16` | 五性别组 |

例如筛选怪兽组：

```text
9B 05 00 00 00 00 01 07 01
```

服务端从已加载的 `Pokemon.jsonc` 图鉴数据中找出包含该蛋组的图鉴 ID，并在宝可梦关联
查询中应用 `pokemon.dex_id IN (...)`。无效索引会被拒绝；物品公开列表不应用蛋组条件，

刷新当前 GTL 页面时复用。

### 性别规则 `1`

规则 `1` 后跟一个 unsigned byte，取值含义为：

| 值 | 枚举 | 含义 |
| ---: | --- | --- |
| `0` | `MALE` | 雄性 |
| `1` | `FEMALE` | 雌性 |
| `255` | `GENDERLESS` | 无性别 |

例如查询雄性宝可梦：

```text
9B 02 00 00 00 00 01 01 00
```

服务端根据 `Pokemon.jsonc` 中每个图鉴条目的 `genderRatio` 生成查询条件，并使用
`personality_value` 的低 8 位判断性别：低字节大于等于比例为雄性，小于比例为雌性；
比例 `255` 的图鉴条目为无性别。性别条件与名称索引、性格和闪光条件同时生效，总数查询、
分页查询以及上架、购买、取消后的当前页面刷新都会复用该条件。物品公开列表不应用宝可梦
性别条件；“我的挂单”会保留物品条目，仅筛选其中的宝可梦条目。

### 闪光规则 `8`

规则 `8` 后跟一个 unsigned byte，取值含义为：

| 值 | 含义 | 数据库条件 |
| ---: | --- | --- |
| `0` | 任意闪光，包含秘密闪光 | `is_shiny = true OR is_secret = true` |
| `1` | 秘密闪光 | `is_secret = true` |
| `2` | 普通闪光 | `is_shiny = true AND is_secret = false` |
| `3` | 不闪光 | `is_shiny = false AND is_secret = false` |

例如查询所有闪光宝可梦：

```text
9B 07 00 00 00 00 01 08 00
```

服务端会把闪光类型保存到当前 Session 的 GTL 请求状态。总数查询、分页查询以及
上架、购买、取消后的当前页面刷新使用相同条件。物品公开列表不应用宝可梦闪光条件；
混合的“我的挂单”只筛选其中的宝可梦条目，并保留物品条目。

### 粒子规则 `12`

规则 `12` 后跟一个 unsigned byte 粒子 ID。该值与 `//addparticle` 写入的
`pokemon.particle_effects` 数组使用相同的 ID。`0..38` 表示指定粒子；特殊值
`0xFC`（十进制 `252`）表示任意粒子，只要数组中至少存在一个粒子就匹配。

例如筛选粒子 ID `5`（客户端显示为眼瞳粒子）：

```text
9B 02 00 00 00 00 01 0C 05
```

例如筛选所有至少拥有一个粒子的宝可梦：

```text
9B 03 00 00 00 00 01 0C FC
```

服务端对 `0..38` 使用 PostgreSQL 数组包含条件
`particle_effects @> ARRAY[粒子ID]`；对 `0xFC` 使用
`cardinality(particle_effects) > 0`。该条件会保存到 Session，并在上架、购买、取消后的当前页面
刷新时复用；物品公开列表不应用粒子条件，“我的挂单”会保留物品条目，仅筛选其中
的宝可梦条目。

### 已学习技能规则 `16`

规则 `16` 后跟一个 unsigned short LE 技能索引 ID。服务端将该 ID 与
`pokemon.moves` 的四个当前已学习技能槽进行数组包含匹配；`can_remember_moves`
（可回忆技能）不会被用于本规则。技能索引必须为正数且不超过 `SMALLINT` 的最大值。

例如筛选当前已学习技能索引 ID `1`：

```text
9B 0A 00 00 00 00 01 10 01 00
```

服务端使用 PostgreSQL 数组包含条件
`moves @> ARRAY[技能索引ID]::smallint[]`。该条件会保存到 Session，并在上架、购买、
取消后的当前页面刷新时复用；物品公开列表不应用技能条件，“我的挂单”会保留物品条目，
仅筛选其中的宝可梦条目。

### 隐藏特性规则 `13`

规则 `13` 后跟一个 unsigned byte。当前抓包确认客户端使用 `0` 和 `1`：

| 值 | 含义 | 数据库条件 |
| ---: | --- | --- |
| `0` | 有隐藏特性 | `has_hidden_ability = true` |
| `1` | 无隐藏特性 | `has_hidden_ability = false` |

服务端会校验索引范围，并将该条件保存到 Session。公开列表和“我的挂单”中的宝可梦条目
都会应用，物品条目在混合列表中不受影响。上架、购买、取消后的当前页面刷新会复用该
条件。字段对应 `pokemon.has_hidden_ability`，与宝可梦条目编码中的隐藏特性稀有度位一致。

例如筛选有隐藏特性：

```text
9B 04 00 00 00 00 01 0D 00
```

### 特性规则 `20`

规则 `20` 后跟一个 unsigned short LE 全局特性索引 ID。日志中的请求：

```text
9B 07 00 00 00 00 01 14 9E 00
```

其中 `0x009E = 158`，服务端输出：

```text
规则类型: 20 (POKEMON_ABILITY)
宝可梦特性限制索引: 158
```

数据库的 `pokemon.ability` 保存的是该宝可梦在图鉴能力数组中的槽位（通常为 `0..2`），
不是全局特性 ID。服务端会根据已加载的 `resource/pokemon/Pokemon.jsonc` 建立
`(dex_id, ability slot)` 映射，再使用对应的 `pokemon.dex_id` 与 `pokemon.ability` 组合条件筛选，
因此重复能力也会正确匹配。能力 ID 必须为 `1..32767`；未知能力 ID 返回空的宝可梦结果。
该条件会保存到 Session，并在公开列表、“我的挂单”以及上架/购买/取消后的当前页面刷新中复用；
物品条目不受此规则影响。

### 隐藏仅雌性种族规则 `21`

规则 `21` 不携带额外字段，表示从结果中排除图鉴性别比例为 `254` 的雌性限定种族。抓包示例：

```text
9B 02 00 00 00 00 01 15
```

服务端日志会输出：

```text
规则类型: 21 (HIDDEN_ONLY_FEMALE)
隐藏仅雌性种族: true
```

服务端从已加载的 `Pokemon.jsonc` 图鉴数据建立雌性限定图鉴 ID 集合，并使用
`pokemon.dex_id NOT IN (...)` 排除。该条件保存到 Session，在公开列表、“我的挂单”和页面刷新中
复用；物品条目不受宝可梦种族条件影响。

### 隐藏百变怪规则 `22`

规则 `22` 不携带额外字段，表示从结果中排除百变怪（图鉴 ID `132`）。用户提供的抓包为：

```text
9B 02 00 00 00 00 01 16
```

服务端日志会输出：

```text
规则类型: 22 (HIDDEN_DITTO)
隐藏百变怪: true
```

### 形态变化已解锁规则 `24`

规则 `24` 不携带额外字段。用户提供的抓包为：

```text
9B 09 00 00 00 00 01 18
```

服务端日志会输出：

```text
规则类型: 24 (ALT_FORM_UNLOCKED)
形态变化已解锁: true
```

客户端实际使用“图鉴 ID `492` 且稀有度短整型包含 `0x0100` 位”判定该条件。
当前服务端数据库只有宝可梦当前形态字段，没有独立的形态解锁稀有度位，因此不会把
`form_type` 或 `dex_id = 492` 误当作已解锁。为避免返回错误结果，公开宝可梦列表在该
规则下返回空页；“我的挂单”混合列表仅保留物品条目。该规则及其结果会保存到 Session，
页面刷新时保持一致。

### 时装部位规则 `33`

规则 `33` 后跟一个 unsigned byte，表示物品页的时装部位。客户端抓包示例（`listType = 1`
为道具商品，部位索引 `0` 为额头）：

```text
9B 07 01 00 00 00 01 21 00
```

服务端日志会输出：

```text
规则类型: 33 (ITEM_FASHION_SLOT)
时装部位限制索引: 0 (FOREHEAD)
```

当前支持的部位索引为：

| 索引 | 部位 |
| ---: | --- |
| `0` | 额头（`FOREHEAD`） |
| `1` | 帽子（`HAT`） |
| `2` | 发型（`HAIR`） |
| `3` | 眼睛（`EYES`） |
| `4` | 脸部/面部毛发（`FACIAL_HAIR`） |
| `5` | 背部（`BACK`） |
| `6` | 上衣（`TOP`） |
| `7` | 手套（`GLOVES`） |
| `8` | 鞋子（`FOOTWEAR`） |
| `9` | 裤子（`LEGGINGS`） |

服务端按客户端 `SkinType` 的 item index 映射筛选，而不是依赖可能不完整的物品元数据：

道具部位规则影响，物品条目按相同范围筛选。

### 头目规则 `14`

规则 `14` 后跟一个 unsigned byte。当前抓包确认：

| 值 | 含义 | 当前处理 |
| ---: | --- | --- |
| `0` | 头目（Alpha） | `is_alpha = true` |
| `1` | 普通宝可梦 | `is_alpha = false` |
| `2` | 命中注定的相遇 | 暂未实现，查询结果为空 |

`0/1` 使用 `pokemon.is_alpha` 筛选，并保存到 Session 供主动刷新复用。项目当前没有表示
“命中注定的相遇”的明确 `pokemon` 字段；因此 `2` 不会错误复用 `egg_value`、捕获地址
或其他字段，而是保持协议可解析并返回空结果。后续补充明确数据字段后，再单独实现该值。

宝可梦条目按客户端 `f.bl_1` 的顺序编码：

```text
listingId: long LE
listingType: byte             // 0 = Pokemon
unitPrice: int LE
createdAt: int LE             // UTC epoch seconds
expiresAt: int LE             // UTC epoch seconds
amount: short LE
[ownStatus: byte]             // 仅 listType = 2
[soldAmount: short LE]        // 仅 listType = 2
[itemIndexPlaceholder: short] // 仅 listType = 2，客户端固定读取
[itemFlagPlaceholder: byte]   // 仅 listType = 2，客户端固定读取
hasPokemonData: byte          // 1
PokemonCodec payload
ivs: 6 * short LE
```

物品条目按客户端 `f.bl_1` 的顺序编码：

```text
listingId: long LE
listingType: byte             // 1 = Item
unitPrice: int LE
createdAt: int LE             // UTC epoch seconds
expiresAt: int LE             // UTC epoch seconds
amount: short LE
[ownStatus: byte]             // 仅 listType = 2
[soldAmount: short LE]        // 仅 listType = 2
itemIndexId: short LE
colorId: byte                 // 无颜色时为 0
```

客户端将 `itemIndexId` 用于加载物品资源，将最后一个 byte 传给时装颜色/变体显示。公开
物品页全部条目之后还固定读取价格表：`count: unsigned byte`，再读取 `count` 组
`unitPrice: int LE + itemIndexId: short LE`。服务端当前发送空价格表 `count = 0`。

## 数据库状态

`db/schemas/init.sql` 新增 `gtl_listing` 和 `gtl_trade_history`。活跃宝可梦和物品挂单使用
`(listing_type, object_id)` 部分唯一索引防止重复上架，并记录原 PC 槽位供后续取消或
过期回收使用。上架事务同时锁定 `character` 与目标 `pokemon`，写入挂单、扣除金钱，
再把宝可梦移动到 `container_id = 6` 的 `auction` 容器。

物品上架事务锁定 `character` 与目标 `owned_item`，扣除费用后把完整记录移入 `void`，
或拆分出新的 `void` 记录。当前 `original_container_id` 字段沿用既有 schema；物品挂单
写入原主背包 ID `1`，`original_container_position` 写 `0`，仅作为以后实现物品返还时的
来源标记。

现有数据库必须先应用新增 DDL；本次代码没有自动修改运行数据库，也没有手改 jOOQ
生成代码。GTL 表暂时通过 `GtlSchema` 的 jOOQ 动态表字段访问；具体上架、查询和结算操作由各自的 GTL 领域服务负责。
PostgreSQL 的 `TIMESTAMP` 在该动态查询中由 JDBC 返回为 `java.sql.Timestamp`；服务端
按该类型读取 `created_at`、`expires_at`，再以 UTC 转换为响应中的 epoch 秒，避免把
JDBC 时间对象直接强制转换为 `LocalDateTime`。

`gtl_trade_history` 以 `listing_id`、买卖双方、挂单类型、成交时的物品索引或宝可梦图鉴、
数量、单价、总价和成交时间记录每次购买。部分物品挂单每次购买各写一行，不能只依赖
`gtl_listing.sold_amount`，否则无法识别购买者和分笔时间。历史表也通过动态 jOOQ 字段访问，
