# 宝可梦粒子选择封包

## 协议

| 项目 | 值 |
| --- | --- |
| opcode | `0x18` |
| 方向 | C2S（客户端 -> 游戏服务器） |
| payload 长度 | 9 字节 |
| 字节序 | little-endian |

客户端精灵面板点击粒子效果时发送：

```text
18 00 10 82 0b 9f 01 00 00 00
```

去除 opcode 后，payload 字段为：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 8 | `pokemonId` | 宝可梦 Object ID，`long LE` |
| 8 | 1 | `particleEffectId` | 粒子类型。`0..38` 为粒子索引，`0xFD` 表示启用随机粒子模式，`0xFF` 映射为服务端的 `-1`（取消选择）。 |

服务端只接受完整的 9 字节 payload，并验证宝可梦属于当前角色的 PARTY 或 PC。`0` 是客户端保留的闪光出场粒子值：普通闪光和秘密闪光都使用它，但客户端会根据同一封包中的 `SECRET` 稀有度位选择不同出场特效；`0xFF`（清除选择）可以直接选择。其他粒子必须出现在宝可梦已拥有的 `particle_effects` 列表中。`0xFD` 映射为服务端的 `-3` 随机模式，仅要求宝可梦至少拥有一个有效粒子，不会在本次请求中抽取具体粒子。

处理成功后，服务端按 `pokemon.id + trainer_id` 更新 `current_select_particle_effect_type`，其中随机模式持久化为 `-3`；同步在线 `PokemonData`，再发送 S2C `0x16`，只设置当前粒子效果更新位（`8388608`）。由于客户端普通宝可梦显示路径只接受正粒子 ID，`PokemonCodec` 和 `UpdatePokemonDataCodec` 在容器/普通增量包中会从已拥有的有效粒子临时投影一个正 ID，避免重进游戏后被当成无粒子；该投影不会改写数据库或在线对象中的 `-3`。进入战斗时，客户端战斗粒子播放器不会处理 `0xFD` 随机哨兵，收到该值会跳过粒子创建，因此 `BattleTeamPokemonCodec` 和 `BattleDebutPokemonCodec` 会在编码时从已拥有的可渲染粒子中解析一个正 ID。随机候选会排除 `0..3` 的保留类型，并兼容旧数据中保存的质子道具索引（由 `Item.bin` 的 `itemParticleEffectType` 转换为客户端质子类型）。同一只宝可梦在一场战斗中第一次编码时确定结果，后续队伍、出场和换位封包复用同一个 ID，退出战斗后清除缓存。数据库失败、角色上下文缺失、宝可梦不存在或粒子未解锁时只记录警告并忽略请求，不主动断开 Session。

## 证据与未验证项

客户端反编译的 `fn_1` 使用 `super(24)`，并依次写入 `CH0.Sa`（8 字节）和 `QL.D7`（1 字节），与上述抓包一致。客户端 `QL.Uy0` 的字节值为 `-3`，即线上 `0xFD`；抓包 `18 00 10 42 A5 C5 00 00 00 FD` 确认它用于随机模式。客户端普通宝可梦状态可以保存该哨兵，但战斗出场逻辑收到 `QL.Uy0` 会直接跳过粒子播放器创建，并不会从列表随机选择；因此服务端战斗 Codec 必须先投影实际的正粒子 ID。`0xFF` 清除选择是根据客户端 `QL` 的 `-1` 哨兵值兼容处理，尚未通过实际客户端操作抓包单独验证；如果客户端始终使用 `0` 表示清除，服务端仍兼容该值。
