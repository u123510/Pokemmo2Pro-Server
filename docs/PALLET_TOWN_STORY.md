## 改造范围

保留地图资源、商店、自定义 NPC、通用对话封包和所有现有角色存档。

## 模块边界

- `org.pokemmo.gameserver.game.story`：开场配置、阶段判定、会话续播、每玩家 NPC 投影、原生对话和动画编排。
  允许依赖角色、地图、宝可梦/战斗模型、既有封包和剧情持久化服务；不直接执行 SQL。
- `org.pokemmo.gameserver.services.story`：角色进度、初始宝可梦领取和首次战斗结算事务。
  允许依赖 Database/jOOQ、剧情进度模型和宝可梦模型；不持有客户端会话或发送封包。
- `ScriptManager` 只加载内容，`CharacterEventService`、`SceneInteractionService` 和 packet 只转交剧情入口。

## 存档约定

本期开场复用 `character.oak_lab_status`，不新建数据库表、不运行迁移、不清空旧数据。

| 值 | 含义 | 重登行为 |
| --- | --- | --- |
| 0 | 尚未触发大木拦路 | 在真新镇北出口触发 |
| 1 | 已遇见大木，前往研究所 | 从护送检查点恢复 |
| 2 | 等待选择初始宝可梦 | 不再播放拦路剧情 |
| 3 | 已领取初始宝可梦，等待首次劲敌战斗 | 不再赠送宝可梦 |
| 4..9 | 开场已结束或旧版后续阶段 | 不再触发开场 |

`first_partner_status[0]` 沿用旧资源实际写入顺序：0=妙蛙种子、1=小火龙、2=杰尼龟、3=未选择。
数据库数组下标从 1 开始。旧枚举注释曾把后两项写反，不据此批量修正已有玩家。
开场模块不更改 `oak_parcel_status`。该字段现由独立 [包裹与图鉴章节](OAK_PARCEL_STORY.md) 管理，
阶段 4 之后可继续领取/交付包裹，交付进入阶段 5，图鉴和五球奖励完成后进入阶段 6。

初始宝可梦插入、图鉴记录和阶段 2→3 在一个带角色/账号条件的事务内提交。
首次劲敌战斗只有服务端判定胜负后才能完成，胜负均结束教学战斗；客户端回执不能伪造完成。
已完成标记不回退，断线后仅从未完成检查点继续。妈妈治疗仍可重复使用。

旧玩家若进度一直未落库，不能只凭“现在有宝可梦”推断开场已完成，也不能自动赠送或重置资产。
此类存档需先核对旧数据，再由维护者明确标记完成；本次不操作实际数据库。

## 当前流程

1. 未开始玩家踏入真新镇北出口 `(12,1)` 或 `(13,1)`，保存阶段 1，大木拦路并靠近。
2. 确认对话后，大木与玩家移动至研究所门前；进入研究所等待真实 C2S `0x05`，再走到博士面前。
3. 播放研究所介绍及劲敌对话，最后保存阶段 2，玩家自由选择三只初始宝可梦。
4. 点击精灵球显示原生宝可梦预览及是/否框；确认后事务发放 5 级初始宝可梦，记录图鉴和阶段 3。
5. 到研究所出口或与大木/劲敌交互，进入原生首次劲敌战斗；对手使用克制玩家初始选择的宝可梦。
6. 服务端确认胜/负后保存完成阶段 4，恢复队伍 HP/PP/异常状态；胜利奖励 80，失败不扣钱。
   奖励、战斗中的等级/经验/EV 和完成标记一起保存，重复结束通知不会重复发钱。
7. 完成玩家重登不重播开场；妈妈仍提供治疗。之后可进入常磐市商店，接续独立的
   [包裹、图鉴及五球奖励剧情](OAK_PARCEL_STORY.md)，不提前将后续章节标记完成。

这是服务端重建的开场流程，并非直接运行完整原版脚本。对白沿用旧资源中已记录的原生文本引用，
不复制整套 ROM。镜头、门动画、劲敌取球行走等精确逐帧还原不属于已验证能力；
当前护送使用服务端地图寻路与原生行走包。客户端/ROM 版本差异及整段演出仍需实机核对。

## 协议依据

- 复用既有 S2C `0x21` 对话：序号 byte、类型 byte、文本引用 int LE、实体 ID long LE、延迟 int LE、格式参数。
- C2S `0x21` 严格两字节：原样回传序号、选择值。普通继续为 0；是为 1、否为 0。
- 客户端源码依据：`f.kt_0.Oj0`、`f.iw_1.m80`、`f.Ge0.ze0`、`f.on_0.ig0` 和 `f.Q7` 的按钮回调。
- S2C `0x0D` 行走、`0x11` 位置、`0x12/0x08` NPC 显示/移除、`0x24` 宝可梦预览、`0x30/0x31` 战斗，均不改字段。
- 领取后用 `0x14` 增加宝可梦、`0x0A` 同步图鉴；治疗/结算用 `0x13` PARTY 快照、`0x0C` 金钱刷新。
- 对话等待有超时清理；动画按已有 `SportType` 时长异步续播。没有已确认的客户端动画完成回执，
  因此不声称动画时间已实测完全一致；换图必须等地图加载确认，不能用固定延时替代。

## 阶段不一致报错

当旧日志显示 `PalletStoryStore.advance` 的“剧情存档与当前步骤不一致”，且来自
`PalletOpeningService.onStep` 的 `0 -> 1` 拦路调用时，按该分支的代码条件：
数据库 `oak_lab_status` 为 `0`，但 `first_partner_status` 第一项为 `0/1/2`，并非未选择的 `3`。
旧日志没有写出具体是哪一种初始选择，不能据此推断是妙蛙种子、小火龙还是杰尼龟。

常见原因是测试重置只改了开场阶段，保留了旧初始选择。两项含义不同：

- `oak_lab_status=0`：剧情还没开始。
- `first_partner_status[1]=0/1/2`：已经选择妙蛙种子/小火龙/杰尼龟。
- `first_partner_status[1]=3`：未选择；这里用的是 PostgreSQL 数组下标 1，Java 数组对应下标 0。

本次补充移动和 NPC 的前置校验，并统一地图确认检查：冲突时不先发起剧情锁定或执行存档更新，
聊天提示与中文错误日志直接列出两个字段的实际值。若对话期间数据库阶段被外部改动，
事务仍会拒绝过期步骤，并报告期望阶段、目标阶段、数据库阶段和数据库初始选择。
这不是自动修复存档，也不是删除防重复领取检查；仍需维护者按真实意图处理数据。

针对日志中的角色 `2`，维护者可自行执行只读核对（agent 未连接数据库）：

```sql
       first_partner_status[1] AS kanto_starter, oak_parcel_status
FROM public."character"
WHERE id = 2;
```

完整退出角色、备份并确认归属后再处理：

1. **全部剧情重玩**：开场阶段改为 `0`，初始选择第一项改为 `3`，包裹状态改为 `3`；
   保留初始选择数组的其余四项和五项长度。提交后完整重登，按下节到真新镇北出口触发。
2. **保留已领取宝可梦继续**：不要把初始选择抹掉。若确实尚未完成首次劲敌战斗，
   核对队伍与旧领取记录后使用阶段 `3` 和真实初始选择；若该战斗已完成，则恢复阶段 `4`
   或已经确认的更后阶段，不把后续完成进度退回。不能只看队伍里有哪只宝可梦就自动推断剧情。

重新走领取节点会再发宝可梦和奖励，旧资产不会自动回收；重玩只用于测试角色。

## 重置后未触发

旧代码的 `onLogin` 只从 `CharacterData` 复制进度。普通角色选择会查询数据库，
但重连复用旧 `CharacterManager` 时可能仍是旧进度；仅在数据库编辑字段不会实时更新在线缓存。
另一个旧边界是阶段 0 只由走路入口触发，直接登录或传送到触发格不会启动。

当前修复：非战斗的登录/重连重新读取数据库的 `oak_lab_status` 和 `first_partner_status`，
仅同步关都剧情字段，不改金钱、队伍、其他地区进度或坐标。查询失败时暂停剧情触发并报中文日志，
不默认为新角色、不回退旧缓存。进行中的战斗保留在线进度，禁止通过外部改表中途重置战斗。
真实地图加载确认后，如果阶段为 0、初始选择为 3、位置已在真新镇触发格且非忙碌，也会启动开场。
