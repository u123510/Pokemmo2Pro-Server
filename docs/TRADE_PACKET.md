# 玩家交易封包

本文档记录附近玩家交易的当前服务端实现。交易不写入单独的交易表；报价保存在在线 `TradeSession`，最终由 `TradeService` 在一个数据库事务中提交。

## 协议

| Opcode | 方向 | 字段 | 说明 |
| --- | --- | --- | --- |
| `0x51` / `0x62` | c2s | UTF-16LE、以零字符结束的玩家名称 | 发起附近玩家交易请求；`0x51` 为官方客户端入口，`0x62` 为抓包兼容入口 |
| `0x21` | c2s | `byte interactTimes`, `byte type` | 交易请求回执；`type == 0` 拒绝，`type == 1` 接受，其他值取消请求 |
| `0x50` | c2s | `byte action` | `0` 取消，`1` 锁定报价，`2` 最终确认 |
| `0x09` | c2s | `byte count`，每项 `byte sourceContainer`, `short sourcePosition`, `byte targetContainer`, `short targetPosition` | 官方 PARTY/PC 与交易容器之间的宝可梦移动 |
| `0x23` | c2s | `short position`, `short action`, `byte container` | 兼容旧入口，添加/移除 PARTY 或 PC 中的宝可梦 |
| `0x24` | c2s | `long ownedItemId`, `short amount` | 兼容旧客户端的道具槽 0 操作格式 |
| `0x53` | c2s | `short slot`, `long ownedItemId`, `short amount` | 设置或清空指定交易道具槽（0..5） |
| `0x50` | s2c | `byte flags`, `byte side`, UTF-16LE 名称 | 打开交易窗口；打开使用 `flags = 3`，关闭由状态包触发 |
| `0x51` | s2c | `byte status` | 交易状态：`1` 完成、`2` 取消、`3` 对方最终确认、`4` 对方锁定 |
| `0x14` | s2c | 完整 `PokemonCodec` 记录 | 更新报价方本侧交易槽；交易报价时使用 `containerId = 2`，`containerPosition` 为交易槽 0..5 |
| `0x52` | s2c | 完整 `PokemonCodec` 记录 | 更新报价方对手侧交易槽；没有 `side` 字段，交易报价时使用 `containerId = 2`，`containerPosition` 为交易槽 0..5 |
| `0x53` | s2c | `byte side`, `int money` | 广播金钱报价 |
| `0x54` | s2c | `byte side`, `short slot`, `long itemId`, `short itemIndexId`, `short amount`, `byte colorId` | 广播道具槽更新；`itemId = 0` 清空槽位 |

字段的字节序为 little-endian，字符串为 UTF-16LE。客户端交易窗口固定六个道具槽和六个宝可梦槽。锁定和最终确认只发送给交易对方，因为客户端会先在本地标记自己的按钮状态。交易完成或取消时服务端发送状态包并清理会话，不再发送 `flags = 0` 的 `0x50`，避免客户端重新创建一个空交易窗口。

NPC 商店不使用以上 `0x23/0x24` 兼容入口进行买卖。适配后的客户端先协商商店扩展，
再通过独立 C2S `0xDC` 携带报价编号和请求序号；因此不会把同长度的商店请求误当作玩家
交易报价。S2C `0x23` 仍是商店窗口，方向不同。详见 [`NPC_SHOP_PACKET.md`](NPC_SHOP_PACKET.md)。

普通宝可梦删除包 `0x15` 只支持客户端映射的 PARTY/PC 等持久容器；客户端没有 `TRADE` 容器的删除映射。交易报价时，服务端向报价方发送 `0x14`，向对方发送 `0x52`：客户端前者写入本侧交易容器，后者固定写入对手侧交易容器。两者的 `containerId = 2` 和交易槽位只覆盖编码输出，不会临时修改在线 `PokemonData`。撤回或失败恢复只恢复原容器记录并由交易状态包关闭窗口，不发送 `0x15 + containerId=2`。

## 状态和回执

1. 发起方和目标必须在线、同频道同地图，且不在战斗或其他交互中；请求等待期间如果双方离开同一地图，接受会被取消。双方 ID 通过双向 pending 索引和请求锁防止重复竞态。
2. 目标在 `0x21` 回执中以 `type = 1` 接受后建立 `TradeSession`，双方收到 `0x50` 打开窗口；`type = 0` 表示拒绝。
3. 金钱、道具和宝可梦改变报价时会清除双方锁定/确认状态。
4. `0x50 action = 1` 锁定自己的报价；双方锁定后，`action = 2` 才能最终确认，并向对方发送 `0x51` 状态回执。官方 `0x09` 的多项交易移动会先整体校验，再一次性更新交易槽。
5. 双方最终确认后进入 `COMMITTING`，期间不能取消或修改报价。事务失败会发送取消状态、关闭会话并重新刷新双方的金钱、PARTY、PC 和背包视图。
6. 成功后进入 `COMPLETED`，发送完成状态和接收方的 `0x14` 新增宝可梦包；接收宝可梦优先写入接收方 PARTY 的空槽，PARTY 无空槽时写入 PC 空槽，随后刷新双方金钱、PARTY、PC 和主背包。
7. 取消、拒绝、超时、断线和重复关闭均为幂等操作；待处理请求 30 秒无回执会自动清理，断线会清理 pending 请求和活动交易。

## 资产边界

- 金钱不能为负，且不能超过提交时角色余额。
- 道具必须属于发起方主背包、未绑定、可交易；可穿戴时装按 `SkinType` 的客户端索引映射允许交易。`0x53` 中的 `long` 是 `owned_item.item_id`，不是 `item_index_id`。
- 如果服务端日志出现“拒绝交易道具”，随后会打印具体原因和 `itemIndexId`。`ItemDataReader` 暴露的 `Item.bin` `isTradeAble` 字段实际是打包字节中的一部分，不能直接当作客户端交易开关；普通物品现在按客户端默认允许交易，再排除客户端已确认的特殊不可交易索引区间。可穿戴时装继续按 `SkinType` 映射允许交易。比如日志中的 `itemIndexId=1476`（对应 `itemId=489987117056`）是有效普通道具，不应因该字段为 `false` 被拒绝。
- 每方最多六个道具槽；堆叠道具可提交 `1..当前数量` 的部分数量。整堆交易转移原记录，部分交易在事务中扣减原记录并创建新的接收记录，同时保留颜色、地区和奖励字段；`ownedItemId <= 0` 且数量为 `0` 用于清空指定槽位。
- 宝可梦必须属于发起方的 PARTY 或 PC，最多每方 6 只；交换后接收方优先使用 PARTY 空槽，剩余宝可梦再写入 PC 空槽（不要求空槽连续），并将接收方本次报价释放的 PARTY/PC 槽位计入可用空槽。提交事务按 `container.name` 读取 PC/PARTY 容器 ID，不依赖数据库自增 ID 固定为 0/1。
- 报价建立后，道具不能销毁、上架交易行或用于换装，宝可梦不能上架交易行；这些旁路操作会被拒绝，避免最终确认前资产被消费。
- 撤回宝可梦时，目标 PARTY/PC 槽位必须为空，或仍是该报价宝可梦原来的槽位；占用槽位的撤回请求会被拒绝。
- 交易窗口打开期间会拒绝地图移动、NPC 对话和普通 PARTY/PC 换位；只有交易容器相关的宝可梦报价/撤回操作可以继续处理。
- 不能把所有 PARTY 宝可梦全部换出；接收方 PARTY 空槽优先使用，剩余数量再按基础 660 格加角色扩容计算 PC 空槽。
- 提交事务按角色、宝可梦和道具 owner 条件加锁；任一资产校验或 SQL 更新失败都会回滚整笔交易，避免并发重复消费、跨角色修改或半笔提交。
